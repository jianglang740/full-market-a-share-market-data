# A股全量市场行情数据：工欲善其事，必先利其器

*Full-market A-share market data: a workman must first sharpen his tools.*

- 量化的本质是用数据流驱动资金流，万丈高楼不能凭空而起，而数据就是建造这座高楼所需要的地基，我在进行多因子量化模型研究时就时常受到数据集不够的问题干扰，而自己通过数据服务商的api拉取耗时耗力，且费用过高，api接口限流严重，于是干脆心一横，购买了服务商的源头数据包，并将其规范整理封存，故而这个项目提供了详尽的A股量价数据，主要用于本地建模研究，出于复杂度和性能考虑，本项目中的数据构建完后就已经冻结，后续不再更新，因为只是本地研究、复现量价因子，这份数据已经足够充实了。

- 数据范围：**1 分钟 K 线 + 日线，2009-01-05 ~ 2026-10-23，Hive 分区 Parquet。**

- 这份数据由购买的第三方 Tushare 口径行情包重排而来，**不含任何数值变换**：
价格一律保持未复权原值，复权因子逐行给出，任何复权口径都可以从这里算出来。
源包在整理完成后我已将其删除，本目录自此**自包含**——重建、校验、统计都不再需要它（见 §7.4）。

> **这是一份冻结数据，不再跟进新数据。**
> 构建时间 2026-10-28，最后一根 K 线是 2026-10-23 15:00。之后的市场不在此数据集内。

> **本仓库只放说明与目录骨架，不含数据本体。**
> 39 GiB 的 parquet 全部在 `.gitignore` 里，仓库中只有 `minute/1min/`、`daily/`、`basic/` 三个空目录

## 零、5 分钟上手

**环境**：标准 Parquet 文件，任何能读 Parquet 的工具都行，不需要专用客户端、不需要联网。
实测环境：Python 3.13 / `pyarrow` 21.0.0 / `pandas` 2.3.3 / `duckdb` 1.5.6（DuckDB 可选）。

**三条查询带期望行数**——跑通且数字对得上，说明分区、压缩、读取都没问题。
（下面的路径都相对于本目录，先 `cd` 进 `A股行情数据/`，或者把路径改成绝对路径。）

```python
import duckdb
con = duckdb.connect()

# ① 某一天的全市场分钟行情
con.execute("""SELECT * FROM read_parquet('minute/1min/year=2024/month=06.parquet')
               WHERE trade_date = DATE '2024-06-03'""").df()          # 1,297,061 行

# ② 某只股票的 18 年分钟历史
con.execute("""SELECT count(*) FROM read_parquet('minute/1min/**/*.parquet', hive_partitioning = true)
               WHERE ts_code = '000001.SZ'""").fetchone()             # 1,041,843 行

# ③ 一整年的日线
con.execute("SELECT count(*) FROM read_parquet('daily/year=2024.parquet')").fetchone()  # 1,293,893 行
```

对不上先跑 `_build/02_verify.py`（§7.2），别急着怀疑自己的代码。

**读之前先想清楚粒度**：

- 一个月的分钟文件约 **2,300 万行**，十列全读进 pandas 约 **2 GB**；只选需要的列能省一大截。
- `read_parquet('minute/1min/**/*.parquet')` 是 **214 个文件 / 36.5 亿行**，绝对不要一次性 `.df()`，
  按年、按月或按 `ts_code` 过滤后再取；跨年分析请分日/分月迭代，不要在内存里堆全量。

### 1.1 每个目录是干什么的

| 路径 | 内容 | 规模 | 主键 | 什么时候用它 |
|---|---|---|---|---|
| `minute/1min/year=YYYY/month=MM.parquet` | 1 分钟 K 线，每股每分钟一行，10 列（§2.1） | 214 个文件<br>3,647,449,745 行<br>37.1 GiB | `(trade_date, ts_code, trade_time)` | 日内因子、开盘/收盘行为、量价微结构；带 `open`，日内收益率可直接算 |
| `daily/year=YYYY.parquet` | 日线，每股每天一行，33 列（§2.2） | 18 个文件<br>14,790,365 行<br>0.98 GiB | `(trade_date, ts_code)` | 日频因子；涨停 / 停牌 / ST 过滤；市值、换手、估值 |
| `basic/dim_instrument.parquet` | 证券主表（码表），不含行情（§1.2） | 5,928 行 × 17 列<br>191 KiB | `ts_code` | 给结果贴行业标签、按板块筛股、查上市日期 |
| `_manifest.json` | 构建清单：每个 parquet 的行数 / 字节 / md5 / 来源 | 214 + 18 条 | — | 判断文件有没有被改动过（§7.1） |
| `_build/_audit.json` | 逐年逐月的股票数、交易日数、行数、档数分布 | — | — | 不读 38 GiB 就知道每年有哪些数据 |
| `_build/*.py` | 生成 / 校验 / 统计脚本 | 3 个 | — | 重建或体检（§7.2、§7.3） |

三个数据目录之间**只靠 `ts_code` 关联**，没有外键、没有全局索引。

### 1.2 `basic/dim_instrument.parquet` 是什么

一张**证券主表**（对应 Tushare 的 `stock_basic`），**不是行情数据**：一行一只股票、没有日期维度，
5,928 行 = 5,928 个 `ts_code`。含已退市股票（§3.2），所以比任一交易日的在市家数多
（2026 年在市约 5,597 只）。

17 列分三类（逐列说明见 §2.3）：

| 类别 | 列 | 说明 |
|---|---|---|
| 标识 | `ts_code` / `symbol` / `name` | `ts_code` 与 `minute`、`daily` 完全同构，可直接 join |
| 分类 | `industry` / `market` / `exchange` / `area` | 行业（源数据原始值，申万口径未校准）、板块、交易所、地域 |
| 日期 | `list_date` | **本表唯一有值的日期列**：上市日 |
| 无用 | `list_status` / `delist_date` / `is_hs` / `fill_source` | 四列全空，退市日拿不到（§6.3） |

> 多数日频因子不需要它——`daily` 已自带 `is_st`、市值、换手率。
> 它的实际价值在两列：`industry`（行业中性化）和 `list_date`（算"上市满 N 天"）。

### 1.3 分区命名

年月都遵守 Hive 的 `key=value` 命名约定，但**只有目录名会被引擎自动识别成列**：

```
minute/1min/year=2024/month=06.parquet
            └───────┘  └──────────┘
            目录：自动成为 year 列    文件名：只是命名，不自动成列
```

- `year` 是**目录级分区键**。DuckDB 用 `read_parquet('.../**/*.parquet', hive_partitioning = true)`
  读时会多出 `year` 列（INTEGER）；pyarrow 用 `HivePartitioning` 同理。
- `month` 写在**文件名**里，两者引擎都**不会**解析成列。要某个月，直接在路径里写
  `year=2024/month=06.parquet`，比造一列再过滤更直接（见 §4.1）。
- 分区键不重复写进文件内部——文件里没有 `year`/`month` 列，数据本身已有 `trade_date`。
- 想按月份范围筛选，用 `trade_date` 即可：文件内按 `trade_date` 排序、行组带 min/max 统计，
  不依赖目录名也能剪枝。

### 1.4 为什么按月分区

三种可能的切法，对比：

| 切法                               | 文件数        | 查"某一天全市场"        | 查"某只股票全历史"         |
| ---------------------------------- | ------------- | ----------------------- | -------------------------- |
| 每股一个文件（源 zip 的做法）      | 6.6 万        | 要开 5,000 个文件，很慢 | 1 个文件，最快             |
| 每天一个文件                       | 4,300         | 1 个文件，最快          | 要开 4,300 个文件          |
| **每月一个文件（本数据集）** | **214** | 1 个文件内按行组剪枝    | 18 年 = 214 个文件，可并行 |

月度分区是这两种访问模式的折中，同时把文件数压到 214，元数据开销可以忽略。
因子研究的两种主力查询——横截面（某天全市场）和时间序列（某只股票）——都不吃亏。

### 1.5 文件内部结构

- **排序键**：`(trade_date, ts_code, trade_time)` 升序。同一交易日的全部股票连续存放。
- **行组**：约 100 万行一个 RowGroup，每个行组带 `trade_date` 的 min/max 统计。
  所以 `WHERE trade_date = '2024-06-03'` 只会读命中的行组，不会扫完整个文件。
- **压缩**：zstd level 3 + 字典编码。`trade_date`、`ts_code` 在按日排序后字典命中率极高，
  这是 36.5 亿行只有 38 GiB 的主要原因（源 zip 解压后约 70 GB）。

## 二、字段字典

### 2.1 `minute/1min/*.parquet` —— 10 列

| 列名           | 类型          | 单位         | 含义                                                                |
| -------------- | ------------- | ------------ | ------------------------------------------------------------------- |
| `trade_date` | timestamp[ns] | —           | 交易日，时间部分恒为 00:00:00                                       |
| `ts_code`    | string        | —           | 代码，带交易所后缀：`.SZ` / `.SH` / `.BJ`（如 `000001.SZ`） |
| `trade_time` | timestamp[ns] | —           | 该 K 线的**结束时刻**（见 §5.2）                             |
| `open`       | double        | 元           | 该分钟内第一笔成交价，**未复权**                              |
| `high`       | double        | 元           | 该分钟内最高价，未复权                                              |
| `low`        | double        | 元           | 该分钟内最低价，未复权                                              |
| `close`      | double        | 元           | 该分钟内最后一笔成交价，未复权                                      |
| `vol`        | double        | **股** | 该分钟成交量                                                        |
| `amount`     | double        | **元** | 该分钟成交额                                                        |
| `adj_factor` | double        | —           | 复权因子（见 §5.1）                                                |

**注意单位**：分钟表的 `vol` 是**股**、`amount` 是**元**；日线表的 `vol` 是**手**、`amount` 是**千元**。
两边差 100 倍和 1000 倍（已实测：同一股票-日两边比值恰好是 0.01 和 0.001）。混用时必须换算。

### 2.2 `daily/year=*.parquet` —— 33 列

**价格与量**

| 列名                    | 单位 | 含义                                                    |
| ----------------------- | ---- | ------------------------------------------------------- |
| `open/high/low/close` | 元   | 未复权                                                  |

| `vol`                 | 手   | 成交量                                                  |
| `amount`              | 千元 | 成交额                                                  |

**交易约束**

| `suspend_timing`            | 停牌时段（空 = 未停牌）                                                                     |
| `suspend_type`              | 停牌类型                                                                                    |
| `is_st`                     | 是否 ST（1/0）                                                                              |
| `listed_days`               | 截至当日的上市天数                                                                          |

**估值**

| 列名                                    | 含义                                       |
| --------------------------------------- | ------------------------------------------ |
| `pe` / `pe_ttm`                     | 市盈率（静态 / TTM）                       |
| `pb`                                  | 市净率                                     |
| `ps` / `ps_ttm`                     | 市销率                                     |
| `dv_ratio` / `dv_ttm`               | 股息率                                     |
| `turnover_rate` / `turnover_rate_f` | 换手率（总股本口径 / 自由流通股本口径，%） |
| `volume_ratio`                        | 量比                                       |

**股本与市值**

| 列名                                               | 含义                                     |
| -------------------------------------------------- | ---------------------------------------- |
| `total_share` / `float_share` / `free_share` | 总股本 / 流通股本 / 自由流通股本（万股） |
| `total_mv` / `circ_mv`                         | 总市值 / 流通市值（万元）                |

`adj_factor` 同分钟表。

> 估值、股本、市值这几列在原数据包里是 `double`，**单位按 Tushare 惯例为万股/万元**，
> 本数据集未做任何换算。第一次使用建议拿一只股票和公开数据对一眼再批量用。

### 3.2 覆盖特点

- **含已退市股票**：全部 5,928 只代码中，2024 年有数据而 2026 年已无的有 103 只，其历史仍在。

- **无 5/15/30/60 分钟线**：这些可以由 1min 精确聚合得到（量额相加、OHLC 取极值），
  保留等于同一份数据存六遍。需要时现算。

## 四、怎么用

### 4.1 DuckDB

```sql
-- 某一天的全市场分钟行情
SELECT * FROM read_parquet('minute/1min/year=2024/month=06.parquet')
WHERE trade_date = DATE '2024-06-03';

-- 某只股票的全部历史（214 个文件并行读）
SELECT * FROM read_parquet('minute/1min/**/*.parquet', hive_partitioning = true)
WHERE ts_code = '000001.SZ';

-- 某个月的横截面：每天每只股票的日内波动率
SELECT trade_date, ts_code, stddev_samp(close) / avg(close) AS intraday_vol
FROM read_parquet('minute/1min/year=2024/month=06.parquet')
GROUP BY 1, 2;
```

`**` 通配全部年份目录；`hive_partitioning = true` 会把**目录名**解析成 `year` 列
（`month` 在文件名里，不会被解析——见 §1.3）。即便不写 `WHERE year = ...`，
DuckDB 也会用目录和行组统计跳过不相关的数据。

### 4.2 pandas / pyarrow

```python
import datetime as dt
import pyarrow as pa
import pyarrow.dataset as ds

# 一个月、一天：路径里写死分区最省事
tbl = ds.dataset('minute/1min/year=2024/month=06.parquet', format='parquet').to_table(
    filter=ds.field('trade_date') == dt.datetime(2024, 6, 3))

# 全部年份：把 year 目录解析成列再过滤
dset = ds.dataset('minute/1min', format='parquet',
                  partitioning=ds.HivePartitioning(pa.schema([('year', pa.int32())])))
tbl = dset.to_table(filter=ds.field('year') == 2024)
```

> `pyarrow.dataset.partitioning(...)` 在 pyarrow 21 里不接受位置参数形式的字段元组
> （`('year','month')` 会报 `Expected Schema`），必须传 `pa.schema`。

### 4.3 复权

见 §5.1。**做收益率时不需要事先复权**——直接用 §5.1 的公式，或者用日线表的 `pct_chg`。

### 4.4 常见操作配方

**① 压成每天 240 档**

`09:30` 是单独的开盘集合竞价档，要压成"第一分钟"时按下表合并，其余 `09:32–15:00` 的 239 档原样保留：

| 列 | 取法 |
|---|---|
| `open` | `09:30` 档的 `open` |
| `close` | `09:31` 档的 `close` |
| `high` / `low` | 两档的 `max` / `min` |
| `vol` / `amount` | 两档相加 |

```sql
WITH b AS (
  SELECT * FROM read_parquet('minute/1min/year=2024/month=06.parquet')
  WHERE trade_date = DATE '2024-06-03'
    AND CAST(trade_time AS TIME) <= TIME '09:31:00'
)
SELECT ts_code, trade_date,
       max(CASE WHEN CAST(trade_time AS TIME) = TIME '09:30:00' THEN open  END) AS open,
       max(high) AS high, min(low) AS low,
       max(CASE WHEN CAST(trade_time AS TIME) = TIME '09:31:00' THEN close END) AS close,
       sum(vol) AS vol, sum(amount) AS amount
FROM b GROUP BY 1, 2;
```

> ⚠️ 这条规则只在**本数据集内部**成立，**不要**指望它和别的数据源逐档对齐。
> 实测拿合并结果与另一套同区间的分钟数据比对：2024-06 一周 25,508 个股票-日，
> 合并后的量平均只有对方的 97.8%，单个股票-日在 31%–272% 之间。
> 不同数据源对开盘集合竞价的切分方式不同——跨源分析请统一用一套数据，不要逐档拼。

**② 前复权到指定基准日**

```sql
WITH base AS (                          -- 每只股票最新交易日的因子
  SELECT ts_code, arg_max(adj_factor, trade_date) AS f_last
  FROM read_parquet('daily/*.parquet') GROUP BY 1
)
SELECT d.trade_date, d.ts_code, d.close,
       d.close * d.adj_factor / b.f_last AS close_qfq
FROM read_parquet('daily/*.parquet') d JOIN base b USING (ts_code);
```

基准日想换成别的某天，把 `f_last` 换成那天的 `adj_factor` 即可。
实测 000001.SZ 2024-06-14 除权：原始价 10.80 → 10.18（−5.7%，假跌），
前复权价 8.8724 → 8.9604（+1.0%，真实涨跌）。

**③ 单位换算**

| 想从 | 到 | 乘 |
|---|---|---|
| 日线 `vol`（手） | 股 | ×100 |
| 日线 `amount`（千元） | 元 | ×1000 |
| 日线 `total_share` / `float_share` / `free_share`（万股） | 股 | ×10,000 |
| 日线 `total_mv` / `circ_mv`（万元） | 元 | ×10,000 |
| 分钟 `vol` / `amount` | 已是股 / 元 | — |

自校验：`total_share × close` 应等于 `total_mv`。实测 000001.SZ 2024-06-13：
1,940,591.82 万股 × 10.80 元 = 2,095.8 亿元 = `total_mv`。

## 五、口径说明

### 5.1 未复权 + `adj_factor`

所有价格都是**未复权**原始成交价。`adj_factor` 是逐行给出的复权因子，只在除权除息日跳变。

```
后复权价  = 原价 × adj_factor
前复权价  = 原价 × adj_factor / adj_factor_最新
真实收益率 r_t = (close_t × adj_factor_t) / (close_{t-1} × adj_factor_{t-1}) − 1
```

**为什么存未复权**：复权基准是一个分析决策（基准日选哪天、用前复权还是后复权），
把它冻进数据集就等于替使用者做了决定。存原价 + 因子是唯一不失真的表示。

> 本数据集的 `adj_factor` 与米筐（RiceQuant）的口径不同，实测同一股票同一日
> 相差约 3.2%。两者都是"自洽的复权因子"，只是归一化基准不同。
> **不要把它和别的数据源算出的收益率混在一张表里比较**——跨源对齐要先统一基准。

### 5.2 时间戳与每日档数

`trade_time` 是 K 线的**结束时刻**（依据：午后第一档是 `13:01` 而不是 `13:00`）。

正常股票每交易日 **241 档**：

```
09:30                         开盘集合竞价（单独一档）
09:31 – 11:30                 上午连续竞价，120 档
13:01 – 15:00                 下午连续竞价，120 档
```

`09:30` 这一档是集合竞价，与 `09:31` 合计约等于连续竞价的第一个分钟。
如果你的分析框架要求"每天 240 档"，把 `09:30` 并入 `09:31` 即可。

**北交所例外**：`.BJ` 个股在部分交易日是 **271 档**，多出 `15:01–15:30` 共 30 档。
实测这些档位**全部是零成交量、价格冻结在 15:00 收盘价**的填充行，不是真实成交。
过滤方式：

```sql
WHERE CAST(trade_time AS TIME) <= TIME '15:00:00'
```

对所有股票都适用——它只会命中北交所那些填充行，正常股票的最后一档本来就是 15:00。

该现象正好从 `.BJ` 数据出现的那个月（2022-07）开始，但之后分布不规律——
2025-11、2025-12、2026-01 ~ 2026-08 这几个月的 `.BJ` 个股又恢复成 241 档。

### 5.3 `pre_close` 与 `pct_chg`

日线表的 `pre_close` **不是**前一日的 `close` 原值，而是**按当日因子重算过的昨收**：

```
pre_close_t = close_{t-1} × adj_factor_{t-1} / adj_factor_t
```

实测：000001.SZ 2024-06-14 除权，`prev_close = 10.80`，`pre_close = 10.08`，
比值 0.9333 = 1 / 1.0714（当日/前日因子比）。

因此 **`pct_chg` 已经是扣除除权除息影响后的真实收益率**，可以直接用于因子计算，
不需要再乘因子。

### 5.4 价格精度

A 股最小报价单位 0.01 元，所有价格字段都是两位小数（`double` 存储，值本身无更多精度）。
不存在浮点量化误差，但也不要期待超过 0.01 元的分辨率。

## 六、已知问题

### 6.1 2009 年缺 15 只股票的分钟数据

原始 `2009` 年压缩包里有一批成员损坏（CRC 校验失败 / 文件头不完整），读取时已跳过：

```
000045.SZ 000046.SZ 000048.SZ 000049.SZ 000050.SZ 000056.SZ 000059.SZ
000060.SZ 000062.SZ 000063.SZ 000065.SZ 000066.SZ 000070.SZ 000078.SZ 000088.SZ
```

影响：这 15 只在 **2009 年的分钟数据**缺失；日线不受影响（日线来自另一个文件，
15 只都在），2009 年之前之后也都不受影响。其余 17 个年份的数据抽样各 250–320 只全部完好。

修复方式：若日后重新拿到 2009 年的原始分钟数据，用 §7.3 的命令重跑该年即可补上。
明细在 `_manifest.json` 的 `corrupt` 字段。

### 6.2 2026 年不完整

只到 2026-10-23，且 2026 年 1–8 月数据完整、9–10 月可能仍有遗漏。
把它当作"截至 2026-10-23 的快照"使用，不要当作完整年度。

### 6.3 码表状态列为空

`list_status` / `delist_date` / `is_hs` / `fill_source` 四列全空（见 §2.3）。
退市判断只能靠行情数据的缺失，不能靠码表。

### 6.4 北交所零成交量填充档

见 §5.2。不影响价格，但会破坏"每天固定 241 行"的假设，
按日 pivot 或 reshape 之前先过滤。

### 6.5 量额单位

分钟表 `vol`=股 / `amount`=元，日线表 `vol`=手 / `amount`=千元。
两表直接对比会差 100 倍 / 1000 倍。

### 6.6 停牌日在分钟表里是满 241 档的零成交量填充

停牌当天，**分钟表仍给出完整 241 档，但 `vol` 和 `amount` 全为 0、OHLC 全部冻结在停牌前收盘价**；
**日线表则没有这一天的行**。两种处理方式不一致，直接混用会出问题。

半天停牌同理：日线有行且 `suspend_timing` 标出停牌时段（如 `13:00-15:00`），
分钟表在停牌时段给出零成交量、价格冻结的档（实测 `000594.SZ` 2014-01-02：241 档里 123 档零成交量，
`vol` 合计 39,457,120 股 = 日线的 394,571.22 手）。

全库 15,110,765 个股票-日中，这种零成交量日有 **379,324 个（2.5%）**，分布很不均匀：

| 年份 | 占比 | 年份 | 占比 |
|---|---|---|---|
| 2009–2013 | 3.5% – 4.9% | 2019–2021 | 0.2% – 0.4% |
| 2014 | **8.1%** | 2022–2023 | 1.4% / 0.8% |
| 2015–2018 | 4.7% – 8.0% | 2024–2026 | 0.1% – 0.3% |

实测样本：`000520.SZ` 2014 全年 244 个交易日、58,804 档，`vol` 合计 0、`close` 只有 2.53 一个值——
这只股票当年确实整年停牌，日线表里一行都没有。

**处理建议**：

```sql
-- 只用分钟数据时，自己剔除停牌日
SELECT trade_date, ts_code
FROM read_parquet('minute/1min/year=2014/*.parquet')
GROUP BY 1, 2
HAVING sum(vol) > 0;

-- 或者和日线对齐（日线没有停牌行，join 自然剔除）
SELECT m.* FROM read_parquet('minute/1min/year=2014/*.parquet') m
JOIN read_parquet('daily/year=2014.parquet') d USING (trade_date, ts_code);
```

注意 `2019` 年之前日线表也偶有整只股票整年缺失的情况（同上 `000520.SZ`），
这时 join 剔除是对的；**不要**把它当成分钟数据缺行。

### 7.1 `_manifest.json`

```jsonc
{
  "minute": {
    "2024-06": {
      "path": "minute/1min/year=2024/month=06.parquet",   // 相对本目录
      "rows": 23330400,
      "size_bytes": 123456789,
      "md5": "...",            // 文件级指纹
      "parts": 42              // 由多少个临时分片合并而成
    }
  },
  "daily": { "year=2024": { "rows": 1293893, "md5": "..." } },
  "basic": { "rows": 5928, "md5": "...", "note": "..." },
  "source": {                  // 每个年份来自哪个 zip
    "2024": { "zip": "2024.zip", "zip_bytes": ..., "files_1min": 5423, "rows_1min": ... }
  },
  "corrupt": { "2009": [ ... ] },
  "columns": { "minute": [...], "daily": [...] },
  "built_at": "..."
}
```

`path` 是**相对本目录**的路径——整个数据集换位置（例如挪到外接盘）后 manifest 仍然有效。
`md5` 只用于日后判断"文件有没有被改动过"，**不证明内容正确**。
内容正确性由 §7.2 的抽样比对保证。

### 7.2 体检（随时可做，不需要源包）

```bash
# 结构 + 行数 + 档数分布（约 2 分钟）
python -I _build/02_verify.py --out .

# 再加上 38 GiB 的全量 md5 复核（约 5 分钟）
python -I _build/02_verify.py --out . --md5
```

`02_verify.py` 的七项检查：

| # | 检查 | 需要源包 |
|---|---|---|
| 1 | 分区文件数与 `_manifest.json` 一致 | 否 |
| 2 | 月份连续无缺口（2009-01 ~ 2026-10） | 否 |
| 3 | 214 个文件 schema 完全一致 | 否 |
| 4 | 行数守恒：逐分区与 manifest、逐年与 manifest 记录的源行数一致 | 否 |
| 5 | `--md5` 时全量重算 214 个文件校验和（约 38 GiB 读盘） | 否 |
| 6 | 每日档数分布（信息性，不判失败） | 否 |
| 7 | 随机 30 个股票-日与源 zip 逐值比对 | **是**（`--pkg`，源包已删则自动跳过） |

**最近一次执行结果（2026-10-28，数据集定位到本目录后重跑）：1–6 全部通过，
md5 逐个相符；第 7 项 30/30 与源 zip 逐值相同。** 之后如果把数据集挪动或转存，
建议再跑一次 `--md5`，确认搬运没有损坏。

### 7.3 这份数据是怎么生成的（脚本保留，作记录）

`01_partition.py` 是唯一生成器，做的是：

- 把"每股一个文件"重排成"每月一个文件"
- 按 `(trade_date, ts_code, trade_time)` 排序
- 统一 schema（2026 那批源文件 `ts_code` 是 `large_string`，已统一成 `string`）
- 校验主键唯一并拒绝重复
- 跳过 15 个损坏成员并记入 `_manifest.json` 的 `corrupt`（§6.1）

不做：

- 不改变任何数值
- 不复权、不聚合、不填充、不剔除
- 不合并 `09:30` 档
- 不删除北交所的零成交量填充档

脚本保留在这里，是因为它逐行列出了上面这些决策——**数据本身是自解释的，这些"没做什么"
只有脚本能说清**。源包删除后 `01_partition.py` 不再能直接运行；日后若重新拿到原始 zip
（例如要补 §6.1 的 15 只），按下面的方式跑：

```bash
python -I _build/01_partition.py --pkg "<含逐年 zip 的目录>" --out . --years 2009-2009
```

### 7.4 来源与处置

- 来源：一份购买的第三方行情包（Tushare 口径），其中分钟数据是逐年打包的 zip，
  日线与证券主表各是独立的 Parquet 文件。
- 处置：重排、校验通过后，**源包（约 182 GB）已整体删除**。本目录自此自包含，
  不再依赖、也不再引用它的任何路径。
- 一致性证据：源包删除前做过随机 30 个股票-日的逐值比对（open/high/low/close/vol/amount/adj_factor
  全部 `rtol=0, atol=0` 相同），证明重排没有引入任何数值变化。
